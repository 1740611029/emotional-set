# Design

## Context

三类原始数据由三个独立通道提供，发布时点差别很大（本地文件时间戳实测）：

| 数据类 | 来源 | 实测可得时点 |
| --- | --- | --- |
| 指数日线 | 同花顺公开日线 | T 日 15:01 即为定稿 |
| 机构多空单 | 中金所盘后披露 | T 日 18:19 前已发布 |
| 板块日线 | akshare 申万行业接口 | T 日 16:12 无，T+1 上午才发布 |

旧实现（本次改动前）：启动时首屏直接用落盘数据、后台跑一次新鲜度判定；收盘分支只要"跑过一次"就把当天标记完成；每类每天限 3 次增量刷新。后果是板块数据一旦在 15:00 拿不到，当天不再尝试，次日启动还可能被限次挡掉。

约束：不得改动确认型信号算法与数据口径（AGENTS.md 规则 1/2/5）；补齐期间必须保持单飞锁，避免与盘中 30 秒刷新并发写同一批文件。

## Goals / Non-Goals

**Goals:**

- 让"数据是否已更新"的判定与实际发布时点匹配：一天内多次机会，且失败不留"已完成"的假象
- 启动即反映最新可得数据，不出现"页面指数是今天、板块是昨天"却无人补拉的状态
- 补齐过程全程可观测（阶段、说明、最近错误、尝试次数）

**Non-Goals:**

- 不改任何信号计算逻辑、阈值、确认层数
- 不更换板块数据源（换源影响已单独调研，结论是不换）
- 不引入外部调度系统（cron/任务计划程序），继续用服务内定时器
- 不为板块做盘中实时合成通道（板块无对应实时快照源）

## Decisions

1. **启动改为阻塞式补齐**（`_bootstrap`：原始数据 → `_backfill_blocking` → 首屏构建）
   用户明确要求"先更新之后再启动数据"。代价是板块全量比对约 10–13 分钟内页面显示"数据准备中"，由 `/api/health` 的 `stage/detail` 暴露进度。
   备选：保留后台补齐（首屏快，但用户看到的是旧板块数据）——已被用户否决。

2. **完成标记以"最近已完成交易日"为键，而不是"当天尝试次数"**
   `refresh-state.json` 结构改为 `{日期: {"done": {数据类: 补齐时的预期交易日}, "tries": {数据类: 次数}}}`。`done` 命中且预期日未推进才跳过；跨 15:00 预期日推进即自动失效。`tries` 只用于日志，不再阻止重试 —— 直接满足"失败的不算、下次启动再试"。
   备选：把每日上限调大（仍会出现"当天不试了"）；按次数指数退避（下次启动仍被挡）。

3. **收盘分支与晚间时刻共用一套判定**
   `_tick_close` 只在 `data_gap()["stale"]` 为空时才设 `_close_date`；新增 `_tick_evening` + `EVENING_SLOTS = 17:30/20:00/22:00`。时刻表按自然日重置，积压的多个时刻只执行最靠后的一轮，避免一次失败引发连续全量拉取。
   备选：每 30 秒轮询到发布为止（网络压力与不可控的重试风暴）。

4. **补齐后的重算路径与收盘重算保持一致**
   任一类原始日线变化即重算并原子落盘 `index-signals.json` 与 `sector-trends.json`（指数宽度依赖申万行业日线），随后 `invalidate()` 两个内存 store；机构持仓单独补齐不触发信号重算。

5. **板块换源只做调研、不做切换**
   `pipeline/sector_source_survey.py` 用东财行业板块指数与申万指数跑同一套 `calculate_sector_trend`，比较四态与有向强度；结论写入 `data/research/sector-source-em-vs-sw.{md,json}`。切换数据源等于换掉整套信号历史（规则 5），实测两年样本状态翻转 24.7%，故保持不变。

## Risks / Trade-offs

- [启动可能被长时间阻塞] → 仅在判定落后时才联网；进度经 `/api/health` 可查；补齐失败不阻断启动，页面最坏情况是显示旧数据而不是打不开
- [源当天确实不发布时，每次启动都会重试，重复消耗十几分钟] → 属于用户选择的取舍；可用 `重建信号数据.bat rebuild` 或正常启动前的判定日志观察，`--force` 仅在标记一致时强制再拉
- [晚间补齐与盘中 tick 并发] → 沿用 `_refresh_lock` 与 `_lock` 分层，补齐期间不写内存快照，完成后统一 invalidate
- [同一进程内多次启动时刻重叠] → 积压时刻只跑最靠后一轮，且按日重置

## Migration Plan

无数据迁移：`refresh-state.json` 旧格式（`{日期: {数据类: 次数}}`）读入后按"无 done 标记"处理，即当天首次运行会再补一次，之后自动写成新格式。回滚只需还原 `server/scheduler.py` 与 `pipeline/bootstrap.py`。

## Open Questions

- 申万板块日线的确切发布时点仍需 1–2 个交易日观察（17:30 是否已可得），可由晚间补齐日志直接给出答案
- 若后续确认 17:30 恒定拿不到，是否把首个补齐时刻后移（需用户确认后再调 `EVENING_SLOTS`）
